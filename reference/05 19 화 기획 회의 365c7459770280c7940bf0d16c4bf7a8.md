## 1. 서비스 방향성

Life-Log는 일본의 DX 흐름에 맞춰 기획·제작하되, 초기 서비스 재개는 **한국 시장 한정**으로 진행한다.

서비스 안정화 및 기능 고도화 이후에는 **글로벌 서비스 확장**을 목표로 한다.

핵심 방향은 단순한 가계부 앱이 아니라, **아날로그 서류의 DX화**를 기반으로 사용자의 생활 데이터를 관리하고, 실질적인 편의 기능을 제공하는 서비스로 확장하는 것이다.

---

## 2. 핵심 컨셉

### 기본 컨셉

- 종이 서류, 계약서, 보험 서류, 영수증 등을 디지털화
- OCR을 통해 텍스트 인식
- 문서 종류에 따라 자동 분류
- 만기일, 갱신일, 소비 기록 등을 관리
- 사용자가 자주 앱을 열 수 있도록 소비 데이터 기반 기능 추가

### 서비스 이용 빈도 개선 필요성

서류 관리 기능은 특성상 사용 빈도가 낮을 수 있다.

예를 들어 보험 서류나 집 계약서는 만기 시점에만 확인할 가능성이 높다.

따라서 Life-Log는 단순히 서류를 보관하는 앱이 아니라, 영수증과 소비 데이터를 활용하여 **사용자가 더 자주 방문할 수 있는 서비스**로 설계한다.

## 3. OCR 및 AI 분류 방식

## OCR 처리 흐름

사용자가 서류 또는 영수증을 업로드하면 OCR API를 통해 이미지 내 텍스트를 인식한다.

1. 사용자가 이미지 또는 파일 업로드
2. OCR API로 텍스트 인식 요청
3. OCR API가 인식된 텍스트를 String 값으로 반환
4. 반환된 텍스트를 기반으로 문서 종류 및 내용을 판단
5. 분류 결과에 따라 알림, 저장, 분석 기능으로 연결

### OCR API 후보

- Google OCR API
- Naver CLOVA OCR

OCR API는 텍스트 인식만 수행하므로, 반환된 String 값을 기반으로 서비스 내부에서 직접 판단 로직을 구현해야 한다.

---

## 4. LLM 활용 방향

OCR 결과값을 LLM에 전달하면 문서 유형이나 내용을 분류할 수 있다.

다만 모든 처리를 LLM에 의존하는 것은 지양한다.

### LLM 전체 적용 시 우려 사항

- 외부 통신으로 인한 처리 속도 저하
- API 비용 증가
- 응답 정확도 편차
- 서비스 안정성 저하 가능성

### 적용 방향

로직으로 명확하게 분류 가능한 문서는 자체 로직으로 처리한다.

분류가 애매하거나 기타 항목으로 떨어지는 경우에만 AI를 활용한다.

### 정리

- 기본 분류: 자체 로직 처리
- 예외 케이스 / 기타 분류: LLM 활용
- 목적: 정확도, 처리 속도, 비용 효율성 확보

---

## 5. 문서 분류별 기본 알림값

분류된 서류의 종류에 따라 기본 알림 시점을 다르게 설정한다.

| 문서 종류 | 기본 알림 시점 |
| --- | --- |
| 보험 관련 서류 | 만기 1개월 전 |
| 집 계약서 / 임대차 계약서 | 만기 3개월 전 |
| 기타 계약서 | 추후 정책에 따라 설정 |
| 영수증 | 소비 분석 데이터로 활용 |

기본값은 문서 유형에 따라 자동 설정하되, 사용자가 직접 수정할 수 있도록 한다.

## 8. 서비스 이용 빈도 향상 아이디어

## 8-1. 반복 소비 학습 기반 푸시 알림

사용자의 반복 소비 패턴을 학습하여 적절한 시점에 앱 푸시 알림을 제공한다.

### 예시

- 매월 반복되는 고정 지출 알림
- 특정 카테고리 지출 증가 알림
- 평소보다 소비가 많은 시점 안내
- 구독 / 정기결제 예상 알림
- 카드 혜택과 연결 가능한 소비 패턴 안내

이를 통해 사용자가 단순히 계약 만기 시점에만 앱을 여는 것이 아니라, 일상적인 소비 관리 목적으로도 앱을 사용할 수 있도록 한다.

---

## 8-2. 소비 패턴 기반 카드 추천

영수증 데이터를 기반으로 사용자의 소비가 많은 카테고리를 파악하고, 이에 맞는 카드 혜택을 추천한다.

### 기능 흐름

1. 영수증 OCR 인식
2. 소비 카테고리 분류
3. 월별 / 카테고리별 소비 패턴 분석
4. 카드 혜택 데이터와 매칭
5. 사용자에게 적합한 카드 추천

### 카드 데이터 수집 후보

- 카드고릴라 웹크롤링

단순히 카드를 추천하고 끝나는 1회성 기능이 아니라, 사용자의 소비 패턴 변화에 따라 지속적으로 추천 결과를 업데이트하는 방향으로 설계한다.

---

## 8-3. 소비 지역 로그 기능

영수증에 포함된 가게 주소를 인식하여 사용자의 소비 지역을 기록한다.

지도 API와 연동하여 어느 지역에서 소비가 가장 많이 발생했는지 시각화할 수 있다.

### 예시 기능

- 자주 소비하는 지역 표시
- 월별 소비 지역 변화
- 특정 지역 내 소비 금액 합계
- 지도 기반 소비 로그

해당 기능은 중요도가 상대적으로 낮으므로, 핵심 기능 개발 이후 일정이 가능할 때 러프하게 구현한다.

---

## 9-2. NestJS 검토

공통 프레임워크로 **NestJS** 사용을 권장한다.

### NestJS 사용 이유

- TypeScript 기반으로 프론트엔드와 언어 통일 가능
- 프론트엔드 개발자가 서버 개발로 넘어와도 언어 차이가 적음
- 구조화된 프레임워크라 협업에 적합
- Spring과 유사한 구조를 가지고 있음
- 전체 프로젝트의 문법과 개발 방식을 일관적으로 유지 가능

따라서 전체적으로 TypeScript 중심 개발을 검토한다.

---

## 9-3. Python 서버

Python 서버는 분석, AI, 크롤링 관련 처리를 담당한다.

### 주요 역할

- OCR 결과 후처리
- LLM 연동
- 웹크롤링
- 소비 패턴 분석
- 카드 혜택 데이터 수집 및 매칭
- 기타 AI 기반 처리

단순 CRUD는 API 서버에서 처리하고, Python 서버는 AI·분석·크롤링 중심으로 역할을 분리한다.

## 11. 보안 처리

Life-Log는 계약서, 보험 서류, 영수증 등 개인정보 및 민감 정보가 포함된 데이터를 다루므로 보안 처리가 중요하다.

- 파일 접근 시 생체인식 / PIN 인증 적용

- 민감 정보 암호화
- 외부 API 통신 시 보안 처리

## 14. 회의 결론

Life-Log는 단순 가계부 앱이 아니라, **아날로그 서류의 디지털화와 생활 소비 데이터 분석을 결합한 DX 서비스**로 방향을 잡는다.

초기에는 한국 시장 한정으로 서비스를 재개하고, 이후 일본 DX 흐름 및 글로벌 시장 확장을 고려한다.

OCR과 LLM은 모두 활용 가능하지만, 정확도·처리 속도·비용 문제를 고려하여 **로직으로 처리 가능한 부분은 직접 구현하고, 애매한 기타 분류에 한해 AI를 활용하는 방식**으로 설계한다.

또한 서류 관리 기능은 사용 빈도가 낮을 수 있으므로, 영수증 인식·반복 소비 분석·카드 추천·소비 지역 로그 등의 기능을 통해 앱 이용 빈도를 높이는 방향으로 확장한다.
