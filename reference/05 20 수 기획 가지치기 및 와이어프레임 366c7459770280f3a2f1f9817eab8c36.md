## 2. 서버팀 개별 회의 요약

### 인프라 방향

- AWS를 적극 활용하는 방향으로 검토
- 클라이언트와 서버 간 요청은 **HTTPS 기반**으로 처리
- 전체 구조는 확장성과 보안을 고려해 설계

### 기본 아키텍처 구상

- **CloudFront**
    - 정적 사이트 호스팅
    - CDN 역할
    - DDoS 방어의 첫 관문 역할
    - 랜딩페이지 제공 가능
    예: 서비스 소개, 요금제 안내, 사용하기 버튼 등
- **ALB(Application Load Balancer)**
    - 트래픽을 여러 서버로 분산
    - 요청량이 많아질 경우 상대적으로 여유 있는 서버로 요청 전달
    - API 서버 확장 시 필수적인 구조
- **EC2 / API 서버**
    - API 서버는 EC2 위에서 호스팅 예정
    - 애플리케이션 서버는 **NestJS API** 사용 예정
    - 트래픽 증가 시 EC2 인스턴스를 추가로 띄우는 스케일 아웃 구조 검토
    - 기본 서버 수와 최대 서버 수 설정 필요
    - Docker는 복잡도가 높아질 수 있어 현재는 사용하지 않는 방향으로 검토

### 데이터베이스

- API 서버와 DB 서버는 분리해야 함
    - 보안 및 안정성 측면에서 같은 서버에 두지 않는 것이 좋음
- DB는 **Supabase** 사용 예정
    - 무료 용량 5GB까지 사용 가능
    - PostgreSQL 기반
    - 인프라 바깥에 DB를 두어 유지보수 부담을 줄이는 방향

### 인증 / 인가

- 로그인 및 권한 처리를 위해 **JWT 사용 필요**
- 비동기 요청에서도 사용자를 식별하기 위해 요청마다 토큰을 함께 전달
- 인증 방식은 추후 선택
    - 직접 구현
    - AWS Cognito 사용 검토

### 세션 / 캐싱

- ALB를 사용하면 요청마다 다른 EC2로 전달될 수 있어 세션 관리 방식에 주의 필요
- Redis는 세션 저장 및 캐싱 용도로 사용할 수 있음
- 다만 현재 프로젝트에서는 Redis 사용은 우선 제외
- Redis를 사용하는 이유와 구조는 공부해둘 필요 있음

### OCR / LLM 처리 흐름

- OCR 처리는 별도 서버 또는 외부 API 사용 검토
    - CLOVA OCR
    - Google OCR
- 한국어 인식은 CLOVA가 더 적합할 가능성 있음
- 이미지 처리 및 OCR은 메모리 사용량이 크므로 API 서버와 분리하는 방향 검토

### 예상 처리 흐름

1. 사용자가 이미지 업로드
2. OCR을 통해 이미지에서 텍스트 추출
3. 추출된 텍스트를 LLM에 전달
4. LLM이 문서 종류 분류
예: 영수증, 계약서, 기타 문서 등
5. 미리 정한 JSON 템플릿 형식으로 결과 반환
6. 사용자가 결과를 확인 및 수정
7. 최종 컨펌 후 메인 DB에 저장

### 비동기 처리 방식

- OCR 및 LLM 처리는 시간이 걸릴 수 있으므로 비동기 처리 필요
- 검토한 방식
    - AWS Lambda
        - 15분 이내의 가벼운 작업 처리에 적합
        - AWS가 자동으로 스케일링
    - EC2 + 메시지 큐
        - 요청을 줄 세워 순차적으로 처리
        - 과부하 방지 가능
        - 금융 시스템 등에서 자주 사용되는 구조

### S3 스토리지

- 이미지 파일 저장소로 S3 사용 검토
- 업로드 방식은 추후 결정 필요
    - 클라이언트가 S3에 직접 업로드 후 API 서버에 키값 전달
    - 클라이언트가 API 서버에 이미지를 보내고, API 서버가 S3에 업로드
- 보안을 위해 유저별 파티션 구조 필요
- 다른 유저의 파일이 조회되지 않도록 접근 권한 설계 필요
- 이미지 메타데이터 저장 필요
    - 업로드한 유저
    - 업로드 시간
    - OCR 결과 텍스트
    - 문서 종류
    - 파일 경로 / 키값
    - 삭제 여부 등

### 검색 기능

- 추후 문서 검색 기능 강화를 위해 Elasticsearch 사용 가능
- DB 내용을 별도의 검색 서버에 저장하고 빠르게 검색하는 방식
- 예상 검색어 추천, 문서 검색 고도화 등에 활용 가능

## 3. Git / 배포 전략

### 브랜치 전략

- Git Flow 전략 사용 예정
- 브랜치 구조
    - `main`
    - `develop`
    - `feature/기능명`

### 작업 방식

- `develop` 브랜치를 기본 브랜치로 설정
- 각 기능은 로컬에서 `feature/기능명` 브랜치를 생성해 작업
- 작업 완료 후 GitHub에 push
- GitHub에서 Pull Request 생성 후 `develop`으로 merge

### 브랜치 보호 규칙

- 실수로 main 브랜치에 직접 push하지 않도록 보호 규칙 설정
- PR merge 전 테스트 통과 여부를 확인하는 방식 검토
- 문제가 있는 코드는 자동으로 merge되지 않도록 설정 가능

### CI/CD

- PR 또는 merge 발생 시 GitHub Actions가 이벤트 감지
- 빌드 및 테스트 자동 실행
- 빌드 결과물을 EC2 서버에 배포
- 기존 서버를 종료한 뒤 새 빌드 파일로 교체하여 자동 배포
